Architecture walkthrough

Pricecomp 2026 Agent Workflow Architecture

Hexagonal modular monolith for staged ingest, owner-split state, and measurable agent bakeoffs — discussion deck for engineering onboard.

Initiative spine Draft · 2026-08-01 CAP-1 → CAP-10

Motivation

Why rebuild

Token dumps

Full taxonomy (or parent-subtree) prompt dumps burn context that search should supply.

Conflated stages

Discover / assign / extract in one LLM call — hard to score, impossible to improve independently.

D6 wipe

Re-import can erase validated LLM attributes because import reaches agent-owned state.

No eval

No golden set or shareable cost/accuracy metrics — quality and bakeoffs stay anecdotal.

Near-term product: a comparison-ready product DB — leaf membership, cited traits, shelf + normalized price — not shopper features.

Design paradigm · AD-10 · AD-11

Hexagonal modular monolith

  • Vertical packages — each owns domain, commands/queries, ports, and adapters.
  • Dependencies inward — adapters implement ports; domain stays framework-free.
  • Pure domain — facts in, new state / rejection / unpublished events out; no hidden I/O.
  • One Python backend AD-1 — agent flow, REST, MCP, and import; frontend & legacy remain separate consumers.

State ownership · AD-13

One owner per mutable concept

catalog

Source identity, observations, imported facts, shelf-price revisions

taxonomy

Tree, aliases/tombstones, membership, facets, comparable-unit policy

enrichment

Cited trait & quantity revisions

retrieval

Revisioned product embeddings (pgvector)

review

Deferred items, evidence decisions, overrides, re-drive

comparison

Rebuildable indexed projection only

pipeline

Run / stage coordination — not a second business database

Import never writes enrichment. Comparison reads use the projection or one repeatable snapshot — never independently timed owner reads.

Mutation & ingest · AD-14 · AD-2

Command-only mutation + staged pipeline

  • One command handler per business op — expected revisions, domain validation, one Unit of Work (owners + idempotency + projection invalidation + jobs).
  • No adapter SQL — REST, MCP, CLI, agents, LangGraph nodes, and PgQueuer handlers never touch repositories directly.
  • Staged ingest — discover/create → assign → extract; separate prompts, results, and scores. Bulk / single / filtered share the same stages.
  • Stale revisions reject or defer and schedule re-drive — adapters may not stitch multiple mutating commands to fake atomicity.

Process topology · AD-16 · AD-21 · AD-22 · AD-24

API, workers, checkpoints

  • One image, three roles — api, worker, migrate.
  • FastAPI + FastMCP co-hosted; curated MCP at /mcp.
  • PgQueuer dispatches pipeline, re-drive, maintenance — enqueue joins the triggering transaction.
  • LangGraph owns workflow orchestration; AsyncPostgresSaver for orchestration state only.
  • App Postgres owns scheduling & status; checkpoints are not the scheduler.

Hygiene & review · AD-17 · AD-18

Coalesced review — no event journal

  • Immediate checks on assign (structural + per-product semantic), then transactional upsert of one review-request row per stable category scope.
  • Generation fencing — requested_generation / processing_generation + fencing token; expired workers cannot commit completion.
  • Dirtying is precise — reassign / reparent / merge dirties old & new leaves, ancestry, moved subtrees, tombstone scopes — without cascading pending work away.
  • Current tables are authoritative — durable request stores trigger facts + Phoenix refs. No domain-event outbox or journal for taxonomy review.

Identity · evidence · projection · AD-4 · AD-6

Source IDs, evidence, comparison projection

  • Durable source identity — (source_namespace, source_product_id, optional source_variant_id); name/URLs are mutable facts, never identity fallbacks.
  • Evidence on every accepted trait/qty — field, verbatim span, UTF-8 offsets into NFC text, SHA-256, extractor/prompt version — bound to an immutable catalog observation.
  • Deterministic-first extract — unit → price_text → name; LLM only for residual / low-conf / empty.
  • Fail-closed comparison projection — revision-linked rows; mutation invalidates serveability in the same UoW; atomic generation switch on rebuild; no naked cache on quantity rows.

Controlled experiments · AD-20 · AD-35

CAP-10: DB-per-candidate isolation

  • Same harness — identical datasets, ingest slices, commands, models/prompts where controlled, instrumentation, evals, durability.
  • Clone isolation — immutable Postgres baseline (frozen observations, versioned embeddings, taxonomy/config, checksums) cloned into a disposable DB per candidate.
  • Embeddings once — generated into the baseline; read-only during the experiment. Candidates never share a live mutable owner database.
  • No winner early — golden assign (E1), per-stage (E2), cost/item (E3), speed, inspectability must exist first. Cleanup deletes candidate DBs.

Phoenix & telemetry · AD-9 · AD-12

Phoenix + telemetry port

  • Self-hosted Phoenix 19.11.1 — sole trace, dataset, experiment, and run UI; dedicated Postgres DB. No Arize AX / paid tiers as product surface.
  • Thin telemetry port in domain/application — OTel SDK, exporters, OpenInference, Phoenix live only in adapters.
  • Convention pricecomp.telemetry.v1 — run / stage_execution / attempt / item / category IDs; leaf LLM spans only for cost (no parent double-count).
  • Traces default 30-day retention; versioned datasets/experiments persist independently. Phoenix annotations = labels & golden-set inputs, not domain actions.

Migration · AD-15 · AD-28

Side-by-side cutover

  • /legacy — current TypeScript backend + data-importer relocate; /backend becomes the Python monolith root.
  • Freeze & restore-test a read-only legacy baseline; provision new DBs; replay one immutable source manifest — no legacy AI-derived state.
  • Frontend stays on the old API until switch; no flat-taxonomy compatibility layer.
  • Observation window then forward-only recovery — routing rollback pauses new operator writes; never reverse-migrate into legacy.
